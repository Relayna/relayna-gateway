# v1.7.1 release benchmark

The six native amd64 adaptive searches completed 259 fresh-pod trials.
Each selected setting has at least three resource-stable confirmations.

## Runtime and method

Gateway and the harness used [`c6d572ff77e9`](https://github.com/sarattha/relayna-gateway/commit/c6d572ff77e9d7eaf7db40ed3a1f92b8dfccbff5).
Each trial used two fresh Gateway pods, each capped at **2 CPUs, 1 GiB memory,
and a 512 MiB serialized-body budget**. Native amd64 GitHub-hosted runners
built the production image from committed source. Docker, the images, and
kind nodes used the same architecture. The HTTP/1.1 driver sent exact-sized
JSON directly to both pods. The mock verified body length, hash, and credential
stripping, paused reads for 10 seconds, and delayed its response by two seconds.
Gateway used PostgreSQL and Redis. Client, condition, and trial deadlines were
180, 300, and 600 seconds. Upload waiting was disabled.

The workflow dispatched one adaptive search per size. The source command for
each size was equivalent to:

```sh
scripts/bench-body-admission --json run --build --body-mib <size> \
  --repetitions 3 --output target/body-capacity
```

harness identity, request reconciliation, and distinct pod names at each
selected setting. Peaks are per pod. Headroom subtracts the largest observed
cgroup peak from 1,024 MiB. Treat settings as tested lower bounds unless the
adjacent resource edge repeats across at least three observations. These

Across all adaptive trials, 75 trials encountered OOMs,
with 123 restarts and 16,924 transport errors.
Memory was censored in 75 trials. The raw archive retains
failed observations and their setup and measurement diagnostics.

The [v1.7.0 study](v1.7.0.md) also used native amd64. The runs used separate
host allocations and the exact CPU models and traffic outcomes are recorded
per size. The two adaptive studies do not establish a controlled latency or
capacity delta.

At 100 MiB, v1.7.1 offered 4,096 requests per pod and confirmed an edge
at 56 slots, with all three trials at 57 slots recording an OOM. The v1.7.0
study offered 2,048 requests per pod and reached only 255 occupied slots at
its selected setting. Compare these as separate workload observations.
