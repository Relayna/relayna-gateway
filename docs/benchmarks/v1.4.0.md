# v1.4.0 release benchmark

Status: **six-size measurement and evidence audit complete**. Native amd64
validation measured runtime `a45b814cf7f20fe3ff33eaeff28aa77816d92f41` on **14 November 2026 UTC**, Cargo
version **1.4.0**. All six adaptive searches completed **263 fresh-pod
resource trials**, with three resource-stable confirmations per selected
setting. The separate same-runner forwarding-latency comparison also completed.
Final-head CI and required GitHub review remain merge gates.

All six selected settings are **tested lower bounds**. None has a repeatable
adjacent resource edge under the conservative audit. Resource stability and
HTTP-clean delivery are distinct: lost denial replies are explicitly retained.
These workload boundaries require production headroom; they are not recommended
settings or a latency SLO.

## Runtime, harness and protocol

- Runtime and harness: [a45b814cf7f2](https://github.com/sarattha/relayna-gateway/commit/a45b814cf7f20fe3ff33eaeff28aa77816d92f41), clean source builds. Every run verifies its source and script hashes. Benchmark images have version label `unknown`; Cargo/source identity and resolved image IDs are recorded. They are separate from a subsequently signed release image.
- Native Linux amd64 host, Docker, images and kind nodes, without emulation. Six separate Ubuntu 24.04.5 hosts used Docker 28.0.4 and four Docker CPUs; per-size CPU model, memory and timestamps are retained below and in raw provenance.
- Two fresh Gateway pods per trial, each **2 CPUs / 1 GiB / 512 MiB serialized-body budget**, with real PostgreSQL/Redis and the production Distroless image. Authentication/source admission stays enabled. Optional size-aware/elastic modes are unset; the search varies the fixed configured body-slot ceiling.
- Exact 5/10/20/40/80/100 MiB JSON, simultaneous offered cohorts, direct pod endpoints, no TLS/compression/retries. A streaming mock checks body length/hash and credential stripping. It pauses upstream reads for ten seconds and waits two seconds after upload; latency includes those deliberate delays.
- Client, condition and outer deadlines are **180 / 300 / 600 seconds**. RSS and cgroup memory are separate measures. Digest-pinned BusyBox sampling targets 250 ms intervals with 10 ms timestamp resolution; censored failure peaks remain in raw evidence.
- Selected confirmations have complete two-pod memory observations, zero OOMs/restarts, verified admitted bodies and admission gauges drained to zero. Credentials, kubeconfigs and production prompts are excluded from publication.

Each size used this workflow command with `--build` at the committed candidate:

```sh
gh workflow run body-admission-benchmark.yml --ref t3/entra-project-key-discovery \
  -f architecture=amd64 -f mode=full -f body_mib=<5|10|20|40|80|100>
# Workflow execution:
scripts/bench-body-admission --json doctor
scripts/bench-body-admission --json run --build \
  --body-mib <size> --repetitions 3 --output target/body-capacity
```

## Repeated resource observations

Memory is the maximum individual-pod observation across the selected three
confirmations. Headroom is 1,024 MiB minus the observed cgroup peak.

| JSON MiB | Slots/pod | Stable / HTTP-clean trials | Peak occupied bodies/pod | Adjacent OOM trials | RSS / cgroup peak MiB | Headroom MiB |

| 10 | 48 | 3 / 3 | 48 | 49: 2/3 | 926.50 / 1013.67 | 10.33 |
| 20 | 45 | 3 / 3 | 45 | 46: 1/3 | 947.23 / 1017.11 | 6.89 |
| 40 | 31 | 3 / 3 | 31 | 32: 1/3 | 947.20 / 987.75 | 36.25 |
| 80 | 27 | 3 / 1 | 27 | 28: 1/3 | 975.38 / 1006.93 | 17.07 |
| 100 | 32 | 3 / 2 | 32 | 33: 1/3 | 951.06 / 989.74 | 34.26 |

The audit reanalyzes all 263 original trials. A confirmed edge requires at least
three stable confirmations, OOM in every repeated adjacent trial, and no
contradictory lower-slot resource failure at the same cohort. None qualifies;
all six are tested lower bounds. Original harness labels require only one
adjacent OOM, so the audited report corrects those labels without changing any
observations. Original reports and every failed trial remain available.

Occupied bodies include partial uploads. `floor(512 / body MiB)` bounds complete
serialized bodies, not all partially uploaded requests. Higher configured slots
do not imply that many full bodies fit in memory. The selected settings leave
only **6.89–36.25 MiB** observed headroom. Keep the default eight slots and
512 MiB budget unless workload-specific evidence supports a change.

## Controlled comparison and historical context

The [v1.3.0 resource study](v1.3.0.md) used other hosted machines and CPU models.
Matching nominal caps and body sizes do not make these matched hosts. Differences
in selected slot counts are not evidence of a speedup or regression; earlier
observations remain unchanged.

The controlled comparison uses immutable **v1.2.0**, the latest published image
selected at experiment setup; v1.3.0 was merged but had no published release
image then. This does not isolate changes since v1.3.0.

The [same-runner experiment](https://github.com/sarattha/relayna-gateway/actions/runs/43602276708) completed on 14 November 2026 UTC. One native amd64 AMD EPYC 9V74 80-Core Processor host ran candidate then baseline sequentially, with Docker four CPUs / 16760348672 bytes and kernel `7.0.0-1017-azure`. Both use the same harness/fixtures, exact body hash, pod caps and upstream delays: **5 MiB JSON, eight slots/pod, 16 offered requests/pod, three fresh-pod trials per version**. All six trials are HTTP-clean, with zero transport errors, OOMs and restarts.

The candidate is `a45b814cf7f20fe3ff33eaeff28aa77816d92f41`, native image `sha256:703bb3ceeb8a4406794fabbef322cc227a260b903c01f32f40ee7a04e269bdab`. The immutable baseline index is `sha256:a22c3d850ab2c7320d4bf87ce83adf0fa3deb90496fba6a8227a6eea9d885cbf`, source `b0bad48ca38d26a9709403a32dbff00531bb32fb`, resolved native image `sha256:694540502c67e595ea7784e48295ee2f361858e7c36ad5bc93d596d2234e93f5`. The retained OCI manifests verify that identity.
